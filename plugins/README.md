# Breezell Plugin Market

This folder is the Breezell plugin market. Breezell reads `index.json` from here (GitHub first, then
the jsDelivr mirrors) and lists the plugins under **Breezell Console › Plugins**, where they can be
searched, filtered by category, browsed page by page, installed and updated.

| Path | Contents |
|---|---|
| `index.json` | The market index (generated by the devkit, do not edit by hand) |
| `blocklist.json` | Plugins Breezell turns off and will not install (edited by the maintainers) |
| `packages/<publisher.name>/plugin.json` | A plugin's details and all its versions |
| `packages/<publisher.name>/<version>/*.vsix` | The packages (a published version never changes) |
| `devkit/breezell-plugin.mjs` | The devkit: create, build, pack (open or closed source), submit, check |
| `devkit/breezell.d.ts` | The plugin API typings |
| `devkit/templates/`, `devkit/templates.json` | Templates for new plugins (Breezell's "Create a plugin" uses the same) |
| `examples/` | Source of the example plugins, one per kind of plugin (below) |

---

## What a Breezell plugin is

A Breezell plugin is a VS Code extension with a `breezell` object in its `package.json`:

```json
"breezell": {
	"apiVersion": 1,
	"permissions": ["chat.events"],
	"source": "open"
}
```

- It can use the whole VS Code extension API: commands, webview panels, the status bar, settings and so on.
- Give it `"extensionKind": ["ui", "workspace"]` (the templates do). In a remote (WSL, SSH) window it then
  runs on the user's computer, next to Breezell, so `vscode.breezell` is there even when the remote server
  is an older build.
- It also gets `vscode.breezell` to work with Breezell, limited to the permissions it declares.
- Plugins run only while the user is **signed in to Breezell**. Signing out turns them off, and
  `vscode.breezell` refuses every call.
- A plugin works the same whether or not it is in the market: install your own `.vsix` from
  **Plugins › Installed › Install local .vsix**.

## Kinds of plugins

| Kind | What it is | Example | Template |
|---|---|---|---|
| **Pack** | No code: skills, rules for the AI, MCP servers and themes declared in `package.json` | [Starter Pack](examples/starter-pack) | Pack |
| **Panel** | A panel inside Breezell with your own page (a webview), following the conversation | [Focus Player](examples/focus-player) | Panel |
| **AI** | Commands that use the user's chat model | [Doc Writer](examples/doc-writer) | AI command |
| **Window** | A window of its own with your page and layout; it can also open without the editor | [Focus Timer](examples/focus-timer) | Window |
| **Conversation** | Reads the user's conversations, sends messages and approves tool calls, shown in its own window or panel | [Chat Mirror](examples/chat-mirror) | Window |

The kinds combine: one plugin can bring skills, a panel, AI commands and a window.

## Getting started

**In Breezell**

Open **Breezell Console › Plugins › Develop**, fill in the id and name, choose a template (Pack,
Panel, AI command, Window or Minimal) and how to publish it (open or closed source), then pick a
folder. Open the new folder in a new window.

**From the command line** (Node.js 18 or later)

```bash
curl -O https://raw.githubusercontent.com/BreezellCode/BreezellCode/main/plugins/devkit/breezell-plugin.mjs
node breezell-plugin.mjs init my-plugin --id my-name.my-plugin --display-name "My Plugin" --template webview
cd my-plugin
npm install
```

Then open the folder in Breezell and press **F5**: the plugin runs in a development window.

| Command | What it does |
|---|---|
| `npm run build` / `npm run watch` | Bundle `src/extension.ts` into `dist/extension.js` with esbuild |
| `npm run typecheck` | TypeScript type check |
| `npm run validate` | Check `package.json` |
| `npm run package:open` | Pack as **open source**: the source and source maps ship in the package |
| `npm run package:closed` | Pack as **closed source**: minified code only (including the js and css in `media/`), no source, no source maps |
| `npm run submit -- --market <clone of the market>` | Add the package to the market (see "Publishing") |

## The plugin API: `vscode.breezell`

The typings are in [`devkit/breezell.d.ts`](devkit/breezell.d.ts); the templates already have them in
`types/breezell.d.ts`. In other editors `vscode.breezell` is `undefined`, so check it before use.

| API | Permission | What it does |
|---|---|---|
| `breezell.apiVersion`, `breezell.permissions` | — | The API version and the permissions this plugin declared |
| `breezell.account.isSignedIn`, `onDidChangeSignIn` | — | Whether the user is signed in to Breezell |
| `breezell.chat.onDidStartTurn`, `onDidFinishTurn` | `chat.events` | A conversation turn started or finished: mode, outcome (completed, error, stopped) and duration, **never the content** |
| `breezell.chat.listConversations()`, `getConversation(id)`, `onDidChangeConversation`, `show(id)` | `chat.read` | The conversations of this workspace as the user sees them: messages, replies (with reasoning), tool calls with their parameters, status and result, and the memories recalled for each message; the reply being written; open one in Breezell's chat |
| `breezell.chat.send(text, { conversationId })` | `chat.send` | Send a message as the user would, or start a conversation; the AI answers it like the user's own |
| `breezell.chat.approve(id)`, `reject(id)` | `chat.approve` | Approve or reject the tool call a conversation waits for |
| `breezell.models.request({ messages, system, onText, onReasoning }, token)` | `models.request` | Send a request to the user's current chat model, optionally streaming |
| `breezell.models.list()`, `select({ provider, model })` | `models.select` | The models of Breezell's model picker, and switching the chat model to one of them |
| `breezell.providers.listCustom()` | `providers.read` | The user's custom APIs as their settings page shows them: base URL, protocol, request address, **API key**, request headers, account pool, models and prices |
| `breezell.windows.open(id)` | — (the window is declared in `package.json`) | Open one of the plugin's windows; returns it with `postMessage`, `onDidReceiveMessage`, `onDidClose`, `close` |

### Permissions

A plugin declares every permission it uses in `package.json` (`"breezell": { "permissions": [...] }`),
as an Android app does in its manifest. Nothing undeclared is ever usable, and the market lists what
each plugin declares before it is installed.

| Permission | Kind | Granted |
|---|---|---|
| `chat.events` | normal | On from the start; the user can turn it off |
| `models.request` | dangerous | Asked for the first time the plugin uses it |
| `models.select` | normal | On from the start; the user can turn it off |
| `chat.read` | dangerous | Asked for the first time the plugin uses it |
| `chat.send` | dangerous | Asked for the first time the plugin uses it |
| `chat.approve` | dangerous | Asked for the first time the plugin uses it |
| `providers.read` | dangerous | Asked for the first time the plugin uses it, and only for an account whose plan includes Custom API |

- A dangerous permission is asked for once, when the plugin first uses it; the answer is kept. While
  the user has not allowed it, its calls fail with `BreezellPermissionDenied` and the plugin should
  say what it cannot do.
- On the plugin's page (**Plugins › Installed**) the user switches each permission on and off, or
  all of them at once. Turning one off stops it at once, including events the plugin listens to.
- Ask only for what the plugin needs: review looks harder at plugins that read or send messages or
  approve tool calls, and at closed source ones above all.
- `chat.read` gives what the user sees in the chat: never Breezell's prompts, text only the model
  sees, hidden messages or other workspaces' conversations. A tool's parameters and result are cut
  at 20,000 characters. `chat.send` sends at most 10 messages a minute and refuses a busy
  conversation; its messages are billed like the user's own.
- `providers.read` hands out the custom APIs' keys: a plugin can call those APIs itself, outside
  Breezell, and the providers bill the user. It works only for an account whose Breezell plan
  includes Custom API; otherwise the call fails with `BreezellPlanRequired` and the user is not
  asked. It never gives Breezell's own account or other providers' keys.

Rules of `models.request`:

- The first time a plugin uses it, Breezell asks the user. The user can revoke it at any time under
  **Plugins › Installed**.
- A request counts exactly like one the user sends in the chat: Breezell models are billed to the
  user's account, and a custom provider (Custom API) needs a plan that includes Custom API, as the
  server-signed entitlement says.
- The user's rules, skills and memories are not added, and no memory recall runs (no Super Memory quota is used).
- Each plugin may have at most 2 requests running and 20 a minute; a request holds at most 100
  messages and 200,000 characters.
- `onText` gets the whole text so far while the reply streams, `onReasoning` the model's reasoning so
  far while it thinks (models that reason and relays that pass it on), so a plugin can show it is
  working before any text. While a reply is silent Breezell checks that the API still answers (as it
  does for its own background requests): the request fails with `BreezellModelError` when the API
  stopped answering, and after five minutes in all.
- Errors carry a `name`: `BreezellNotSignedIn`, `BreezellPermissionDenied`, `BreezellRateLimited`,
  `BreezellNoModel`, `BreezellInvalidRequest`, `BreezellModelError`, `BreezellCancelled`,
  `BreezellBlocked` (the plugin is on the [blocklist](#blocklist)).

## README in several languages

Breezell shows a plugin's README (as Markdown) on its market page. `README.md` is the English one and is
required. Translations go in the plugin's `i18n/` folder as `i18n/README.<locale>.md`, with these locales:

| Locale | Language |
|---|---|
| `zh-CN` | Simplified Chinese |
| `zh-TW` | Traditional Chinese |
| `ja` | Japanese |
| `ko` | Korean |
| `ru` | Russian |
| `es` | Spanish |
| `pt-BR` | Portuguese (Brazil) |

A user sees the README in Breezell's display language when the plugin has it, and the English one
otherwise. `pack` ships the translations and `submit` publishes them; other `README.*.md` names are left out.

In the README, raw HTML is not shown. Links open outside Breezell (http, https, mailto, or a file of the
market by relative path, shown on GitHub); images load over https or from the market.

## Name, description and commands in several languages

Use VS Code's own mechanism: write `"%key%"` in `package.json`, put the English texts in `package.nls.json`
at the plugin's root and the translations in `i18n/package.nls.<locale>.json` (`zh-cn`, `zh-tw`, `ja`, `ko`,
`ru`, `es`, `pt-br`). `pack` puts the translations at the package's root, where VS Code reads them:

```json
// package.json
"displayName": "%displayName%",
"description": "%description%",
"contributes": { "commands": [{ "command": "focusPlayer.open", "title": "%command.open%", "category": "Focus Player" }] }
```

```json
// i18n/package.nls.es.json
{ "description": "Sonidos ambientales para concentrarte y tu propia música…", "command.open": "Abrir" }
```

So a plugin's root keeps only the English `README.md` and `package.nls.json`; every translation is in `i18n/`
(translations at the root are still accepted).

`submit` puts the translated name and description in the market index: the market shows them in Breezell's
display language, English where a language is missing. Command titles and setting descriptions follow the
editor's display language, as for any VS Code extension. The market also translates the standard categories
(Themes, Programming Languages, Productivity, …); other categories are shown as written.

## Opening a plugin

Users should not need a command to open a plugin. Declare how it opens:

```json
"contributes": {
	"breezell": {
		"launcher": { "command": "focusPlayer.open", "sidebar": true }
	},
	"commands": [{ "command": "focusPlayer.open", "title": "Open", "category": "Focus Player" }]
}
```

- `command`: one of the plugin's own `contributes.commands` (Breezell refuses any other), or
  `window`: one of its windows (`"launcher": { "window": "timer" }`).
- The plugin then gets an **Open** button in Breezell Console › Plugins (market card and Installed page).
- `sidebar` (default `true`): it is also listed by name under **Plugins** in the Box sidebar. Clicking it
  leaves Box for the editor and opens the plugin there (or opens its window). Set `false` to stay out of the list.
- Plugins without an interface (packs, right-click commands) need no launcher.

## Packs: skills, rules, MCP servers

Declare them in `package.json`; no code is needed:

```json
"contributes": {
	"breezell": {
		"skills": ["skills"],
		"rules": ["rules/house-rules.md"],
		"mcpServers": {
			"sequential-thinking": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-sequential-thinking"] },
			"docs": { "url": "https://example.com/mcp" }
		}
	},
	"themes": [{ "label": "My Theme", "uiTheme": "vs-dark", "path": "./themes/my-theme.json" }]
}
```

- `skills`: folders holding skill folders (`skills/<name>/SKILL.md`). They appear in Breezell's skill list
  labelled with the plugin, and the agent loads them like any skill. A user's skill of the same name wins.
- `rules`: Markdown files added to the AI's instructions while the plugin is on (at most 8,000 characters
  per file and 24,000 for all plugins together). Keep them short: they count against every request.
- `mcpServers`: a `command` (with `args` and `env`) or a `url` (with `headers`). They appear in the MCP list
  labelled with the plugin; a user or project server of the same name wins. Users see each command before
  they install.

Everything a plugin declares goes away when it is turned off or removed, and while nobody is signed in.

## Windows

A window plugin declares its windows in `package.json`:

```json
"contributes": {
	"breezell": {
		"windows": [{
			"id": "timer",
			"title": "Focus Timer",
			"entry": "window/index.html",
			"width": 380, "height": 560, "minWidth": 320, "minHeight": 460,
			"requiresEditor": false
		}]
	}
}
```

- The page is the plugin's own HTML, CSS and JavaScript, loaded from `breezell-plugin://<publisher.name>/`.
  It loads `/__breezell/api.js` for `window.breezell`: `postMessage(message)` (to the plugin's code),
  `onMessage(listener)` and `connected`.
- In the plugin's code, `vscode.breezell.windows.open('timer')` opens it (or brings it to the front) and
  returns an object to `postMessage` to the page, listen to `onDidReceiveMessage`, `onDidClose`, and `close()`.
- The window is sandboxed: no Node, no network (`connect-src 'self'`), only the plugin's files, no popups,
  no navigating away, and its own storage (`localStorage`, IndexedDB) separate from Breezell and other
  plugins. The title always ends with the plugin's name.
- Window plugins need `"extensionKind": ["ui", "workspace"]`: the window's files are read on the user's computer.

**Opening without the editor**: with `"requiresEditor": false` a window can open on its own, with no editor
window: from a shortcut that **Plugins › Installed** adds (**Add to Start menu** on Windows, **Add to applications
menu** on Linux: a `.desktop` file, **Add to Applications** on macOS: a small app in `~/Applications` that
Launchpad and Spotlight find), with
`breezell://plugin-window/<publisher.name>/<window id>`, or `Breezell --plugin-window <publisher.name>/<window id>`.
It still needs a signed-in Breezell account; otherwise Breezell opens as usual. A window opened on its own
has no editor to relay messages: `window.breezell.connected` is `false` and `postMessage` resolves to `false`.

### What plugins cannot reach

To protect users and Breezell, plugins get none of these:

- The Breezell sign-in token: `vscode.authentication` gives no `breezell` session.
- API keys, the API Vault, conversation content, system prompts, cloud prompts, memories.
- Breezell's internal commands: `breezell.*` and the other Breezell commands are for Breezell and its built-in extensions only.

## Open or closed source: your choice

| | Open `--open` | Closed `--closed` |
|---|---|---|
| Package contents | Build + `src/` + source maps | Minified build and `media/` only |
| `package.json` | Needs `repository` (https) | Not required |
| In the market | "Open source" badge with a link to the source | "Closed source" badge |

Either way the market shows the package, its SHA-256 and the permissions it declares. Note that
minified JavaScript can still be read: closed source means "no source shipped", not encrypted.

## Publishing to the market

1. Fork [BreezellCode/BreezellCode](https://github.com/BreezellCode/BreezellCode) and clone your fork.
2. In the plugin folder, run `npm run package:open` (or `package:closed`).
3. Run `npm run submit -- --market ../BreezellCode`. The devkit
   - copies the `.vsix` to `plugins/packages/<id>/<version>/`;
   - updates `plugins/packages/<id>/plugin.json` (version, SHA-256, size, permissions) and copies the README and icon;
   - regenerates `plugins/index.json`.
4. Commit and push in your clone, then open a pull request to `BreezellCode/BreezellCode`.

The pull request runs the market check: every package's SHA-256 and size, id, version, permissions
and open or closed source flag must match its entry, and `index.json` must be up to date. Once a
maintainer reviews and merges it, the plugin shows up in Breezell.

**New versions**: raise `version` in `package.json`, pack and submit again. A published version's
contents never change.

### What review looks at

- Ask only for the permissions the plugin needs, and say in the README what they are for.
- Never collect accounts, passwords or API keys, and never imitate Breezell's sign-in or payment screens.
- Never work around billing or plan limits, and never download and run code that was not reviewed.
- Closed source plugins get a stricter review; maintainers may ask questions.

## Blocklist

`blocklist.json` lists plugins that must not run. Breezell downloads it (GitHub and both jsDelivr
mirrors) when it starts, every 30 minutes while it is open, and whenever the market page reloads the
index (Refresh). A window opened on its own (lite mode) downloads it too. A plugin it names:

- is turned off where it is installed, and cannot be turned back on; the user is told why once,
  with **Uninstall** (and **Restart extension host** when the plugin was already running);
- gets nothing more from `vscode.breezell` (every call fails with `BreezellBlocked`) and loses the
  windows it opened, right away, even before the extension host restarts;
- is left out of the market and cannot be installed, from the market or from a local `.vsix`;
- does not open as a window on its own (lite mode) once Breezell has the list that names it.

It works for every extension, not only Breezell plugins, so a blocked plugin cannot escape it by
dropping its `breezell` object. Plugins that were never uploaded are matched by id the same way.

The maintainers edit the file on GitHub:

```json
{
	"plugins": [
		{ "id": "publisher.name", "reason": "Sends the open files to a third-party server." },
		{ "id": "publisher.other", "versions": ["1.0.3"], "reason": "1.0.3 deletes files outside the workspace; 1.0.4 fixes it." },
		{ "publisher": "someone", "reason": "Every plugin of this publisher shows ads.", "l10n": { "zh-TW": "這個發布者的每個插件都會顯示廣告。" } }
	]
}
```

| Field | |
|---|---|
| `id` or `publisher` | One extension (`publisher.name`), or every extension of a publisher. Case does not matter. |
| `versions` | Only these versions; every version when left out. A fixed newer version is offered again as an update. |
| `reason` | Why, in English (at most 500 characters). Users see it. |
| `l10n` | The reason in other languages: `zh-CN`, `zh-TW`, `ja`, `ko`, `ru`, `es`, `pt-BR`. English is shown where there is none. |

The market check (CI) tells which entries are wrong; Breezell leaves a wrong entry out and keeps the
others. After a change, CI also clears the jsDelivr copies; Breezell counts a new entry as soon as one
source has it, and drops a removed one once every source has.
