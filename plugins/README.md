# Breezell Plugin Market

This folder is the Breezell plugin market. Breezell reads `index.json` from here (GitHub first, then
the jsDelivr mirrors) and lists the plugins under **Breezell Console › Plugins**, where they can be
searched, filtered by category, browsed page by page, installed and updated.

| Path | Contents |
|---|---|
| `index.json` | The market index (generated by the devkit, do not edit by hand) |
| `blocklist.json` | Plugins Breezell turns off and will not install (edited by the maintainers) |
| `packages/<publisher.name>/plugin.json` | A plugin's details and all its versions |
| `packages/<publisher.name>/<version>/*.vsix` | The packages (a published version never changes) |
| `devkit/breezell-plugin.mjs` | The devkit: create, build, pack (open or closed source), submit, check |
| `devkit/breezell.d.ts` | The plugin API typings |
| `devkit/templates/`, `devkit/templates.json` | Templates for new plugins (Breezell's "Create a plugin" uses the same) |
| `examples/` | Source of the example plugins, one per kind of plugin (below) |

---

## What a Breezell plugin is

A Breezell plugin is a VS Code extension with a `breezell` object in its `package.json`:

```json
"breezell": {
	"apiVersion": 1,
	"permissions": ["chat.events"],
	"source": "open"
}
```

- It can use the whole VS Code extension API: commands, webview panels, the status bar, settings and so on.
- Give it `"extensionKind": ["ui", "workspace"]` (the templates do). In a remote (WSL, SSH) window it then
  runs on the user's computer, next to Breezell, so `vscode.breezell` is there even when the remote server
  is an older build.
- It also gets `vscode.breezell` to work with Breezell, limited to the permissions it declares.
- Plugins run only while the user is **signed in to Breezell**. Signing out turns them off, and
  `vscode.breezell` refuses every call.
- A plugin works the same whether or not it is in the market: install your own `.vsix` from
  **Plugins › Installed › Install local .vsix**.

## Kinds of plugins

| Kind | What it is | Example | Template |
|---|---|---|---|
| **Pack** | No code: skills, rules for the AI, MCP servers and themes declared in `package.json` | [Starter Pack](examples/starter-pack) | Pack |
| **Panel** | A panel inside Breezell with your own page (a webview), following the conversation | [Focus Player](examples/focus-player) | Panel |
| **AI** | Commands that use the user's chat model | [Doc Writer](examples/doc-writer) | AI command |
| **Window** | A window of its own with your page and layout; it can also open without the editor | [Focus Timer](examples/focus-timer) | Window |
| **Conversation** | Reads the user's conversations, sends messages and approves tool calls, shown in its own window or panel | [Chat Mirror](examples/chat-mirror) | Window |
| **Screens** | Buttons, pages, restyled parts, drawn code fences and modes in Breezell's own screens | [Desk Pet](examples/pet) | — |
| **Companion** | A pet on the chat box that follows what the AI is doing | [Desk Pet](examples/pet) | — |
| **Long-running** | Keeps a conversation going until something is done, with limits and a page of its own | [Goal](examples/goal) | — |

The kinds combine: one plugin can bring skills, a panel, AI commands and a window. For a large plugin
with its own settings page, data downloaded from a GitHub release and a part installed in the system, see
[Breezell IME](examples/ime).

## Getting started

**In Breezell**

Open **Breezell Console › Plugins › Develop**, fill in the id and name, choose a template (Pack,
Panel, AI command, Window or Minimal) and how to publish it (open or closed source), then pick a
folder. Open the new folder in a new window.

**From the command line** (Node.js 18 or later)

```bash
curl -O https://raw.githubusercontent.com/BreezellCode/BreezellCode/main/plugins/devkit/breezell-plugin.mjs
node breezell-plugin.mjs init my-plugin --id my-name.my-plugin --display-name "My Plugin" --template webview
cd my-plugin
npm install
```

Then open the folder in Breezell and press **F5**: the plugin runs in a development window.

| Command | What it does |
|---|---|
| `npm run build` / `npm run watch` | Bundle `src/extension.ts` into `dist/extension.js` with esbuild |
| `npm run typecheck` | TypeScript type check |
| `npm run validate` | Check `package.json` |
| `npm run package:open` | Pack as **open source**: the source and source maps ship in the package |
| `npm run package:closed` | Pack as **closed source**: minified code only (including the js and css in `media/`), no source, no source maps |
| `npm run submit -- --market <clone of the market>` | Add the package to the market (see "Publishing") |

## The plugin API: `vscode.breezell`

The typings are in [`devkit/breezell.d.ts`](devkit/breezell.d.ts); the templates already have them in
`types/breezell.d.ts`. In other editors `vscode.breezell` is `undefined`, so check it before use.

| API | Permission | What it does |
|---|---|---|
| `breezell.apiVersion`, `breezell.permissions` | — | The API version and the permissions this plugin declared |
| `breezell.account.isSignedIn`, `onDidChangeSignIn` | — | Whether the user is signed in to Breezell |
| `breezell.language`, `onDidChangeLanguage` | — | Breezell's display language (`en`, `zh-CN`, `zh-TW`, `ja`, `ko`, `ru`, `es`, `pt-BR`), for a plugin's own texts: `vscode.env.language` does not follow it. Check for it: an older Breezell does not have it |
| `breezell.chat.onDidStartTurn`, `onDidFinishTurn` | `chat.events` | A conversation turn started or finished: mode, outcome (completed, error, stopped) and duration, **never the content** |
| `breezell.chat.listConversations()`, `getConversation(id)`, `onDidChangeConversation`, `show(id)` | `chat.read` | The conversations of this workspace as the user sees them: messages, replies (with reasoning), tool calls with their parameters, status and result, and the memories used for each message (`recalledMemories`, and `memoryUse` with the chat's resident and relevant counts); the reply being written; open one in Breezell's chat |
| `breezell.chat.send(text, { conversationId, automated, mode, model, attachments })` | `chat.send` | Send a message as the user would, or start a conversation; the AI answers it like the user's own. `automated`: the plugin sends it on its own (see [Work over many turns](#work-over-many-turns)). `mode` (`normal`, `agent`, `plan`) and `model` (one of `models.list`) as the pickers set them; `attachments`: up to 10 files or folders of the workspace |
| `breezell.chat.stop(id)` | `chat.send` | Stop the reply a conversation is writing, as Stop does. It is not the user's Stop: `automated` messages may follow |
| `breezell.chat.holdDoneNotice(id)`, `releaseDoneNotice(id, { announce })` | `chat.send` | No done sound or system notification until the work is over (see [Work over many turns](#work-over-many-turns)) |
| `breezell.chat.conversationOfTurn(turnId)` | `chat.read` | The conversation a turn event was about, as `listConversations` names it |
| `breezell.chat.approve(id)`, `reject(id)` | `chat.approve` | Approve or reject the tool call a conversation waits for |
| `breezell.models.request({ messages, system, model, responseFormat, maxOutputTokens, onText, onReasoning }, token)` | `models.request` | Send a request to the user's current chat model, or to `model` (one of `models.list`), optionally streaming. User messages may carry `images` (base64, up to 8). `responseFormat: 'json'` gives the answer parsed in `json`; `maxOutputTokens` caps the answer |
| `breezell.models.list()`, `select({ provider, model })` | `models.select` | The models of Breezell's model picker, and switching the chat model to one of them |
| `breezell.providers.listCustom()` | `providers.read` | The user's custom APIs as their settings page shows them: base URL, protocol, request address, **API key**, request headers, account pool, models and prices |
| `breezell.providers.list()` | `providers.list` | The same custom APIs **without** keys, header values or paths: name, protocol, host, header names, models |
| `breezell.app.requestRestart({ scope, reason, l10n, force })` | `app.restart`; `app.forceRestart` to force | Ask to restart the plugins, this window or all of Breezell, or restart them without asking (see [Restarting Breezell](#restarting-breezell)) |
| `breezell.windows.open(id)` | — (the window is declared in `package.json`) | Open one of the plugin's windows; returns it with `postMessage`, `onDidReceiveMessage`, `onDidClose`, `close` |
| `breezell.tools.register(name, { invoke })` | `agent.tools` | Give Breezell's agent a tool the plugin declares and runs, in the chat modes it picks (see [Agent tools](#agent-tools)) |
| `breezell.tools.registerCallHandler(handler)`, `onDidRunTool` | `agent.hooks` | See each tool call of the agent before it runs, and refuse it; hear how each went (see [The agent's tool calls](#the-agents-tool-calls)) |
| `breezell.permissionState(permission)`, `requestPermission(permission)`, `onDidChangePermissions` | — (only permissions it declared) | Where a permission stands, asking the user at a moment of the plugin's choosing, and hearing when they change it |
| `breezell.chat.readInput()` | `chat.input` | What is in the chat box, its part before the caret, and the recent messages of the conversation |
| `breezell.chat.registerSendHandler(handler)` | `chat.intercept` | See each message before it is sent: change it or stop it (see [A message before it is sent](#a-message-before-it-is-sent)) |
| `breezell.ui.onDidOpenSurface` | — (the page is declared in `package.json`) | One of the plugin's pages opened; returns it with `context`, `postMessage`, `onDidReceiveMessage`, `onDidClose` (see [Changing Breezell's screens](#changing-breezells-screens)) |

### Permissions

A plugin declares every permission it uses in `package.json` (`"breezell": { "permissions": [...] }`),
as an Android app does in its manifest. Nothing undeclared is ever usable, and the market lists what
each plugin declares before it is installed.

| Permission | Kind | Granted |
|---|---|---|
| `chat.events` | normal | On from the start; the user can turn it off |
| `models.request` | dangerous | Asked for the first time the plugin uses it |
| `models.select` | normal | On from the start; the user can turn it off |
| `chat.read` | dangerous | Asked for the first time the plugin uses it |
| `chat.send` | dangerous | Asked for the first time the plugin uses it |
| `chat.approve` | dangerous | Asked for the first time the plugin uses it |
| `providers.read` | dangerous | Asked for the first time the plugin uses it, and only for an account whose plan includes Custom API |
| `providers.list` | normal | On from the start; the user can turn it off. Never a key |
| `agent.tools` | dangerous | "Agent tool registration": asked when the plugin first registers a tool, or when a plugin with MCP servers first runs |
| `agent.hooks` | dangerous | Asked when the plugin first registers a tool call handler or listens to tool runs: it sees what the agent passes (file paths, edits, commands) and the results |
| `app.restart` | normal | On from the start; the user can turn it off. The user still answers each request |
| `app.forceRestart` | dangerous | Asked the first time the plugin forces a restart; if refused, the plugin asks each time instead |
| `editor.read` | dangerous | The plugin asks with `requestPermission`. A plugin is an extension, so VS Code's API reaches open files whatever this says: this is how it says that it does, and how the user tells it not to |
| `chat.input` | dangerous | Asked for the first time the plugin reads the chat box |
| `chat.intercept` | dangerous | Asked when the plugin registers a send handler |
| `ui.contribute` | normal | On from the start; the user can turn it off, which takes the plugin's buttons, pages and modes out of Breezell's screens |
| `ui.modify` | dangerous | Asked when a plugin that declares `ui.patches`, `ui.tokens`, `ui.variants`, `ui.fonts`, `ui.stylesheet` or a companion first runs |
| `chat.render` | dangerous | Asked when a plugin that declares `ui.renderers` first runs: a drawn code fence hands the plugin its text |

- A permission only some versions of Breezell know goes in `"breezell": { "optionalPermissions": [...] }`:
  an older Breezell leaves it out and installs the plugin all the same, where a permission it does not
  know in `permissions` would refuse it. Check before using what it gives.
- A dangerous permission is asked for once, when the plugin first uses it; the answer is kept. While
  the user has not allowed it, its calls fail with `BreezellPermissionDenied` and the plugin should
  say what it cannot do.
- On the plugin's page (**Plugins › Installed**) the user switches each permission on and off, or
  all of them at once. Turning one off stops it at once, including events the plugin listens to.
- Ask only for what the plugin needs: review looks harder at plugins that read or send messages or
  approve tool calls, and at closed source ones above all.
- `chat.read` gives what the user sees in the chat: never Breezell's prompts, text only the model
  sees, hidden messages or other workspaces' conversations. A tool's parameters and result are cut
  at 20,000 characters. `chat.send` sends at most 10 messages a minute and refuses a busy
  conversation; its messages are billed like the user's own.
- `chat.read` also says how many commands a conversation runs in the background, and the tokens its
  replies used as the provider reported them: nothing about money, plans or quota.
- `providers.read` hands out the custom APIs' keys: a plugin can call those APIs itself, outside
  Breezell, and the providers bill the user. It works only for an account whose Breezell plan
  includes Custom API; otherwise the call fails with `BreezellPlanRequired` and the user is not
  asked. It never gives Breezell's own account or other providers' keys.

Rules of `models.request`:

- The first time a plugin uses it, Breezell asks the user. The user can revoke it at any time under
  **Plugins › Installed**.
- A request counts exactly like one the user sends in the chat: Breezell models are billed to the
  user's account, and a custom provider (Custom API) needs a plan that includes Custom API, as the
  server-signed entitlement says.
- The user's rules, skills and memories are not added, and no memory recall runs (no Super Memory quota is used).
- Each plugin may have at most 2 requests running and 20 a minute; a request holds at most 100
  messages and 200,000 characters.
- `onText` gets the whole text so far while the reply streams, `onReasoning` the model's reasoning so
  far while it thinks (models that reason and relays that pass it on), so a plugin can show it is
  working before any text. While a reply is silent Breezell checks that the API still answers (as it
  does for its own background requests): the request fails with `BreezellModelError` when the API
  stopped answering, and after five minutes in all.
- Errors carry a `name`: `BreezellNotSignedIn`, `BreezellPermissionDenied`, `BreezellRateLimited`,
  `BreezellNoModel`, `BreezellInvalidRequest`, `BreezellModelError`, `BreezellCancelled`,
  `BreezellBlocked` (the plugin is on the [blocklist](#blocklist)).

## Work over many turns

A plugin can keep a conversation going until something is done, as the [Goal](examples/goal) example
does. All of this needs a Breezell newer than 1.4.41, and every call is checked against the sign-in and
the plugin's permissions: after a sign-out or a block it hears nothing more and can do nothing more.

```js
const { chat } = vscode.breezell;
await chat.holdDoneNotice(id);                               // no "done" sound for each turn
chat.onDidFinishTurn(async turn => {
	if (await chat.conversationOfTurn(turn.turnId) !== id) return;
	if (turn.outcome !== 'completed') { await chat.releaseDoneNotice(id); return; }   // stopped, or it failed
	const { backgroundCommands, usage } = await chat.getConversation(id);
	if (backgroundCommands?.willEnd) return;                   // its end starts a turn by itself
	if (done(usage)) { await chat.releaseDoneNotice(id, { announce: true }); return; }
	await chat.send('Go on with the tests', { conversationId: id, automated: true });
});
```

- **`automated`** is for a message the plugin sends on its own. It shows in the chat labelled with the
  plugin's name, and the AI is told the user did not type it. It does not count as the user reacting to the
  last turn and does not end up in their memories. Leave it out only for what a person asked to send.
- **Stop holds.** After the user presses Stop on the reply, an automated message fails with
  `BreezellStoppedByUser` until they write again. A message of theirs waiting in the queue goes first: yours
  fails with `BreezellInvalidRequest`, and the end of that turn is your next chance.
- **The done notice** can be held back, and comes once when released with `announce`. Errors still sound.
  A hold ends by itself on Stop, a sign-out, losing `chat.send`, a block, or the plugin stopping.
- **`backgroundCommands`** (`{ running, willEnd }`) says how many commands run in the background, and how
  many of them will end by themselves: servers and watchers do not. It is a count, not what they are.
- **`usage`** on a reply, on a conversation and on a `models.request` answer is the provider's numbers.
  Some providers count cache reads inside `inputTokens`. Subagents and checks that run beside a
  conversation are not in it, and `repliesWithoutUsage` says how many replies reported nothing.
- A turn's `outcome` is `completed`, `error` or `stopped`. A turn waiting for the user's approval has not
  finished, and a plugin should leave approving to the user.

## README in several languages

Breezell shows a plugin's README (as Markdown) on its market page. `README.md` is the English one and is
required. Translations go in the plugin's `i18n/` folder as `i18n/README.<locale>.md`, with these locales:

| Locale | Language |
|---|---|
| `zh-CN` | Simplified Chinese |
| `zh-TW` | Traditional Chinese |
| `ja` | Japanese |
| `ko` | Korean |
| `ru` | Russian |
| `es` | Spanish |
| `pt-BR` | Portuguese (Brazil) |

A user sees the README in Breezell's display language when the plugin has it, and the English one
otherwise. `pack` ships the translations and `submit` publishes them; other `README.*.md` names are left out.

In the README, raw HTML is not shown. Links open outside Breezell (http, https, mailto, or a file of the
market by relative path, shown on GitHub); images load over https or from the market.

## Name, description and commands in several languages

Use VS Code's own mechanism: write `"%key%"` in `package.json`, put the English texts in `package.nls.json`
at the plugin's root and the translations in `i18n/package.nls.<locale>.json` (`zh-cn`, `zh-tw`, `ja`, `ko`,
`ru`, `es`, `pt-br`). `pack` puts the translations at the package's root, where VS Code reads them:

```json
// package.json
"displayName": "%displayName%",
"description": "%description%",
"contributes": { "commands": [{ "command": "focusPlayer.open", "title": "%command.open%", "category": "Focus Player" }] }
```

```json
// i18n/package.nls.es.json
{ "description": "Sonidos ambientales para concentrarte y tu propia música…", "command.open": "Abrir" }
```

So a plugin's root keeps only the English `README.md` and `package.nls.json`; every translation is in `i18n/`
(translations at the root are still accepted).

`submit` puts the translated name and description in the market index: the market shows them in Breezell's
display language, English where a language is missing. Command titles and setting descriptions follow the
editor's display language, as for any VS Code extension. The market also translates the standard categories
(Themes, Programming Languages, Productivity, …); other categories are shown as written.

## Opening a plugin

Users should not need a command to open a plugin. Declare how it opens:

```json
"contributes": {
	"breezell": {
		"launcher": { "command": "focusPlayer.open", "sidebar": true }
	},
	"commands": [{ "command": "focusPlayer.open", "title": "Open", "category": "Focus Player" }]
}
```

- `command`: one of the plugin's own `contributes.commands` (Breezell refuses any other), or
  `window`: one of its windows (`"launcher": { "window": "timer" }`).
- The plugin then gets an **Open** button in Breezell Console › Plugins (market card and Installed page).
- `sidebar` (default `true`): it is also listed by name under **Plugins** in the Box sidebar. Clicking it
  leaves Box for the editor and opens the plugin there (or opens its window). Set `false` to stay out of the list.
- Plugins without an interface (packs, right-click commands) need no launcher.

## Packs: skills, rules, MCP servers

Declare them in `package.json`; no code is needed:

```json
"contributes": {
	"breezell": {
		"skills": ["skills"],
		"rules": ["rules/house-rules.md"],
		"mcpServers": {
			"sequential-thinking": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-sequential-thinking"] },
			"docs": { "url": "https://example.com/mcp" }
		}
	},
	"themes": [{ "label": "My Theme", "uiTheme": "vs-dark", "path": "./themes/my-theme.json" }]
}
```

- `skills`: folders holding skill folders (`skills/<name>/SKILL.md`). They appear in Breezell's skill list
  labelled with the plugin, and the agent loads them like any skill. A user's skill of the same name wins.
- `rules`: Markdown files added to the AI's instructions while the plugin is on (at most 8,000 characters
  per file and 24,000 for all plugins together). Keep them short: they count against every request.
- `mcpServers`: a `command` (with `args` and `env`) or a `url` (with `headers`). They appear in the MCP list
  labelled with the plugin; a user or project server of the same name wins. Users see each command before
  they install. MCP servers give the agent tools, so they need the `agent.tools` permission in
  `breezell.permissions`: they start once the user allows it.

Everything a plugin declares goes away when it is turned off or removed, and while nobody is signed in.

## Agent tools

A plugin can give Breezell's agent tools of its own: it declares each one in `package.json`, with
the chat modes it is offered in, and runs it in its code. It needs the `agent.tools` permission
("Agent tool registration"), which the user is asked for when the plugin first registers a tool.

```json
"activationEvents": ["onStartupFinished"],
"breezell": { "apiVersion": 1, "permissions": ["agent.tools"] },
"contributes": {
	"breezell": {
		"tools": [{
			"name": "get_weather",
			"displayName": "Weather",
			"description": "Current weather for a city. Use it when the user asks about the weather.",
			"modes": ["chat", "agent", "entanglement"],
			"inputSchema": {
				"type": "object",
				"properties": { "city": { "type": "string", "description": "City name" } },
				"required": ["city"]
			}
		}]
	}
}
```

```ts
context.subscriptions.push(vscode.breezell.tools.register('get_weather', {
	async invoke(input, token) {
		const weather = await lookUp(String(input.city), token);
		return weather ? `${weather.summary}, ${weather.celsius} °C` : { text: 'No such city', isError: true };
	},
}));
```

- `name`: 2 to 48 lowercase letters, digits and underscores, not one of Breezell's own tool names. At
  most 16 tools. `description` is what the agent reads to decide when to call it; `inputSchema` is an
  object JSON Schema (left out: no arguments); `displayName` is what the user sees.
- `modes`: one or several of `chat`, `agent`, `entanglement`, `analyze`, `teams` (none: `agent`). In
  any other mode the agent neither sees nor can call the tool, so a set of tools can make a mode of
  its own, for example Chat with a few tools of yours.
- Register the code when the plugin starts (`onStartupFinished`): a tool is offered only while its code
  is registered. Disposing the registration takes it away.
- The agent reaches the tools as those of the MCP server `plugin:<publisher.name>`; the user's "MCP
  tools" auto-approve setting applies to their calls. `input` is checked against `inputSchema`
  first (required properties present; undeclared ones removed unless the schema allows
  `additionalProperties`).
- `invoke` returns text, or `{ text, isError: true }` for a failure the agent should see as one; a
  thrown error is a failure too. Results longer than 400,000 characters are cut. `token` is
  cancelled when the user stops the agent or after 5 minutes.
- If the user refuses, the tools stay registered but unused; turning the permission on later under
  **Plugins › Installed** brings them back at once. Signed out, blocklisted or turned off, nothing is
  offered, and each call is checked again.
- With `chat.read`, a conversation shows each call of a plugin's tool with `plugin: { id, name }`.
- The arguments the agent passes can hold conversation text or file contents: keep them on the user's
  computer unless the tool says otherwise. Review looks closely at plugins with agent tools.

[Chat Mirror](examples/chat-mirror) has two: `pin_note` (Chat, Agent, Entanglement) and `list_notes`
(every mode).

### The agent's tool calls

With `agent.hooks` a plugin sees each tool call of the agent after Breezell's own checks and before it
runs or asks for approval, and can refuse it:

```js
vscode.breezell.tools.registerCallHandler(call => {
	if (call.name === 'run_terminal_cmd' && /rm -rf/.test(String(call.params.command))) {
		return { deny: true, reason: 'No deleting in this repository.' };
	}
	// or nothing: the call goes on
});
vscode.breezell.tools.onDidRunTool(run => console.log(run.name, run.status, run.resultLength));
```

- A call is `{ conversationId, toolCallId, name, params, mcpServer, mode }`; each text in `params` is cut at
  20,000 characters. `conversationId` is the one `listConversations` uses.
- A refused call never runs. The agent reads your plugin's reason, is told not to repeat the call, and the user
  sees it as your plugin's. Repeating the same refused call counts toward Breezell's loop guard.
- An answer later than 3 seconds, or a failure, lets the call go on; all plugins together get at most 6 seconds,
  in id order, and the first refusal decides. A Stop pressed meanwhile ends the call.
- `onDidRunTool` reports each call once its row has finished: `done`, `failed` or `rejected` (by the user), with
  what the chat shows of the result (cut at 20,000 characters, `resultLength` the full length).

## Restarting Breezell

A plugin can ask to restart, or with the user's leave restart without asking. It chooses what:

| `scope` | What restarts | Needed for |
|---|---|---|
| `extensionHost` | The plugins only, the quickest | Running a plugin's new code |
| `window` | This window | What is read when a window opens |
| `app` | All of Breezell, every window | A plugin's `vscode:uninstall` script: it runs at this restart |

**After an install, an update or a removal.** The plugin's code cannot ask then: an updated plugin's old copy runs until the extension host restarts, and a removed plugin is gone. So declare it in `package.json`:

```json
"contributes": {
	"breezell": {
		"restart": {
			"afterUpdate": { "scope": "window", "reason": "The new panel appears after a restart.", "l10n": { "zh-TW": "重新啟動後才會出現新面板。" } },
			"afterUninstall": { "scope": "app", "reason": "Finishes removing it from this computer." }
		}
	}
}
```

`afterInstall`, `afterUpdate` and `afterUninstall` each take a `scope` and a `reason` (at most 300 characters; the user is told why), with `l10n` for other languages. The install dialog lists them. Asking this way needs no permission. Without an `afterUpdate`, Breezell offers to restart the plugins when an updated plugin was running.

**While the plugin runs.** With the `app.restart` permission:

```ts
const restarting = await vscode.breezell?.app?.requestRestart({ scope: 'window', reason: 'The new settings apply after a restart.' });
```

It is `true` when the restart will happen. After the user says **Later**, further requests within 30 minutes return `false` without asking.

**Not asking.** Add `"force": true`, here or in `afterInstall` or `afterUpdate`, and declare the `app.forceRestart` permission. So that no plugin can trap a user in a loop of restarts, or cut off their work:

- The user is asked for the permission the first time. If they refuse, the plugin asks each time instead.
- It happens once per version of the plugin. After that, the plugin asks.
- It waits for a reply being written to end, for at most 10 minutes, and gives a few seconds' notice with your reason.
- A plugin being removed can only ask.

Every restart goes through the usual shutdown, so unsaved files are kept or asked about as in any restart.

An older Breezell does not install a plugin that declares a permission it does not know, so `app.restart` and `app.forceRestart` limit which versions can use the plugin. It ignores `contributes.breezell.restart`, so asking this way works everywhere it can.

## Changing Breezell's screens

A plugin can add to Breezell's screens and change them, in any look and with any framework it likes,
as far as sign-in, plans, quota, approvals and plugin management stay as they are. It does so by
**declaring** what it wants in `contributes.breezell.ui`, and Breezell draws it. Its scripts and CSS
never run in Breezell's own window: only in its own pages, in frames of their own.

All of this needs a Breezell newer than 1.4.41; tokens, fonts, the stylesheet, variants, the number, text
and colour settings, and the parts and properties marked *new* below come in a later version still. List
its permissions in `optionalPermissions` and an older Breezell still installs the plugin, and ignores what
it declares here that it does not know.

| Layer | Declared in | Permission | What it does |
|---|---|---|---|
| Buttons | `ui.buttons` | `ui.contribute` | Entries in places Breezell opens, drawn in Breezell's look |
| Slash menu | `ui.slashCommands` | `ui.contribute` | Rows in the menu that opens at `/` in the chat box |
| Pages | `ui.surfaces` | `ui.contribute` | The plugin's own HTML, with any framework, in an isolated frame |
| Patches | `ui.patches` | `ui.modify` | Hide, move, restyle or replace named parts of the screens |
| Tokens | `ui.tokens` | `ui.modify` | Set Breezell's own design variables: every screen's palette, the accent, cards, the chat's font and bubbles |
| Fonts | `ui.fonts` | `ui.modify` | Font files of the plugin's, for its tokens and patches |
| Stylesheet | `ui.stylesheet` | `ui.modify` | Tokens and patches written as a CSS file |
| Variants | `ui.variants`, `when` | `ui.modify` | Looks that follow one of the plugin's own settings |
| Fences | `ui.renderers` | `chat.render` | A code fence of a language drawn by one of its pages |
| Modes | `ui.modes` | `ui.contribute` | An entry in the mode picker: a built-in mode plus the plugin's instructions |

A plugin needs the permission whichever list it is in (`permissions` or `optionalPermissions`), and
`validate` says when one is missing. An entry that does not pass is left out and the rest stay, so one
mistake does not cost a plugin everything, and the log says why.

### Buttons

```json
{ "id": "countLines", "slot": "code.block.actions", "title": "Count lines", "icon": "list-ordered",
  "command": "acme.countLines", "l10n": { "zh-TW": "計算行數" }, "order": 0 }
```

| `slot` | Where | The command receives |
|---|---|---|
| `chat.input.toolbar` | The row under the chat box | `{ slot, conversationId }` |
| `chat.message.actions` | The actions under a reply | `{ slot, conversationId, messageIndex }`, the index the turn starts at |
| `code.block.actions` | A code block's actions | `{ slot, language, code }`: pressing it hands over that block |

- `command` must be in the plugin's own `contributes.commands`, and cannot have `breezell` in its name.
- `icon` is a [codicon](https://microsoft.github.io/vscode-codicons/dist/codicon.html)'s name.
- At most 2 of a plugin's buttons in one place and 8 in all. Each shows which plugin it is from, and
  the user can hide it by right-clicking it.

### The slash menu

```json
[
  { "name": "goal", "description": "Set a goal", "icon": "target", "l10n": { "zh-TW": "設定目標" } },
  { "name": "goal pause", "description": "Pause the goal", "icon": "debug-pause", "command": "acme.pause" }
]
```

- `name` is one or two lowercase words without the slash, and cannot have `breezell` in it.
- With `command` (one of the plugin's own), picking the row runs it with `{ slot: "chat.input.slash", conversationId }`.
- With none, picking it puts `/name ` in the box to be written on. What is sent then is for the plugin's
  [send handler](#a-message-before-it-is-sent): without one it goes to the AI as an ordinary message.
- At most 8 per plugin. Each row says which plugin it is from. Typing a space means the rest are words: the
  menu keeps only names that go on like that, and closes when none does, so the message can be sent.

### Pages

```json
{ "id": "notes", "title": "Notes", "entry": "ui/notes.html", "slot": "chat.input.above", "height": 64,
  "network": ["https://api.example.com"] }
```

| `slot` | Where | Height up to |
|---|---|---|
| `chat.input.above` | Above the chat box | 320 |
| `chat.messages.top` | Above the messages | 320 |
| `chat.landing` | On the empty chat page | 480 |
| `chat.input.companion` | Floating on the chat box, see [below](#a-companion-on-the-chat-box) | 240 |
| none | Only where a patch or a fence puts it | 2000 |

The page runs in a frame with an origin of its own. It cannot reach Breezell's window, its storage or
its commands, and always shows a line saying which plugin it is from. It loads the plugin's own files
and nothing else, unless it lists https origins in `network`: those it may connect to and load images
and media from, but no scripts or styles. A framework is fine: bundle it into the plugin. Breezell's
theme is available as `--vscode-*` CSS variables.

```js
const vscode = acquireVsCodeApi();
addEventListener('message', ({ data }) => {
	if (data?.type === 'breezell.surface.context') {
		draw(data.context);                     // where it is, without any extension code
	}
});
vscode.postMessage({ __breezellSurfaceReady: true });    // tell me again, I am listening now
vscode.postMessage({ __breezellSurfaceHeight: 240 });    // the room it needs, within what its place allows
```

The context has ids (`conversationId`), and for a fence its `language`, `code` and `messageIndex`. To
talk to the plugin's code, listen to `vscode.breezell.ui.onDidOpenSurface`.

A page in one of the framed places with nothing to show can take no room at all: declare `"height": 0`, or
send `{ __breezellSurfaceHeight: 0 }`, and ask for room when it has something. It stays loaded meanwhile.

### A companion on the chat box

A page that floats on top of the chat box with no frame or line of its own, a pet for one. It takes no room, and everything it draws stays inside its rectangle.

```json
{ "id": "pet", "title": "Desk Pet", "entry": "ui/pet.html", "slot": "chat.input.companion", "width": 96, "height": 96 }
```

It floats over Breezell's screen, so it needs `ui.modify`, and a plugin has one. While the mouse is on it, Breezell says whose it is. Make your page's background transparent. It shows from the first thing it asks for. Its whole rectangle catches the mouse unless it names the parts that should, so keep that small:

```js
vscode.postMessage({ __breezellCompanion: { width: 96, height: 96, left: 120, lift: 0, ms: 0, hidden: false } });
```

`left` is from the left end of the box and `lift` up from it, `ms` how long moving there takes. Any of them can be left out. Each request sets the time anew, so don't repeat a place with no `ms` during a move: that ends it at once. Breezell keeps it on the box, between 32 and 240 pixels wide and tall, and answers with where it really is. While something waits on the user it stays on the box at 96 pixels at most, so ask for less then. After a failed turn it does the same until the user has seen it: a click on it, which Breezell takes and the page never hears, or leaving the conversation. Nothing else in the message goes anywhere.

A frame catches everything over its rectangle, whatever is drawn there, so what is empty in it blocks the chat beneath. Name the parts that should catch the mouse, and the rest lets it through:

```js
vscode.postMessage({ __breezellCompanion: { hit: [{ x: 40, y: 8, width: 100, height: 200 }] } });
```

`hit` is at most 4 rectangles from the frame's top left corner, to send again whenever they change. Without it the whole frame catches the mouse, as a page with buttons anywhere needs. With it Breezell sees the mouse only until it gets onto one of them, so tell it when the mouse leaves. The wheel over your page stays in your page unless you pass it on, and Breezell scrolls the chat only with the mouse over the page:

```js
element.addEventListener('pointerleave', () => vscode.postMessage({ __breezellCompanion: { mouseOut: true } }));
document.addEventListener('wheel', e => vscode.postMessage({ __breezellCompanion: { scroll: { deltaX: e.deltaX, deltaY: e.deltaY } } }), { passive: true });
```

Its page is told, with no text from the chat in any of it:

| Message `type` | With | When |
|---|---|---|
| `breezell.surface.context` | `context: { conversationId, language }` | At the start, and when the language changes |
| `breezell.companion.layout` | `left`, `lift`, `width`, `height`, `boxWidth`, `maxLift`, `restricted`, `zoom` (the window's: divide a distance in `screenX` or `screenY` by it to get your pixels) | It moved, or the room changed |
| `breezell.companion.pointer` | `x`, `y` from its own corner | The mouse moved over the chat, a few times a second |
| `breezell.companion.chat` | `activity` (`none`, `thinking`, `writing`, `working`, `waiting`), `tool` while working (`terminal`, `edit`, `search`, `web`, `other`) | What the chat is doing changed. Needs `chat.events` |
| `breezell.companion.turn` | `outcome` (`done`, `failed`) | A turn in its conversation ended. Needs `chat.events` |
| `breezell.companion.typing` | | A key was pressed in the chat box, at most ten times a second. Needs `chat.events` |

A page is made for each chat box and starts over when the user changes conversation, so keep what must last in the plugin's code. [Desk Pet](examples/pet) is a whole one.

### Settings in Feature Options

A card with your plugin's settings, in Box > Feature Options, drawn by Breezell and saying whose it is. Box search finds it. It needs `ui.contribute`.

```json
"options": {
  "title": "Desk Pet", "l10n": { "zh-TW": "桌面寵物" },
  "items": [
    { "setting": "deskPet.visible", "title": "Show on the chat box" },
    { "setting": "deskPet.size", "title": "Size", "description": "How big she is.", "choices": [
      { "value": "small", "title": "Small" },
      { "value": "large", "title": "Large", "l10n": { "zh-TW": "大" } }
    ] }
  ]
}
```

Each `setting` must be in your own `contributes.configuration`, and one of these:

| Setting | Shows |
|---|---|
| `"type": "boolean"` | A switch |
| `"type": "string"` with an `enum` | `choices` taken from it (2 to 6) |
| `"type": "number"` or `"integer"` with `minimum` and `maximum` (and `multipleOf` for the step) | A slider *(new)* |
| `"type": "string"`, `"format": "color-hex"` | A colour picker, `#rrggbb` *(new)* |
| `"type": "string"` | A text field, up to its `maxLength` or 200 characters *(new)* |

At most 12 settings. One named after Breezell is refused. Breezell also checks at run time that your plugin is the one that registered the setting, so it writes only your own. Your code hears of a change as usual, with `onDidChangeConfiguration`.

### Patches

```json
{ "region": "chat.input.attach", "hide": true }
{ "region": "chat.input.mcp", "order": -1 }
{ "region": "chat.message.user", "style": { "borderColor": "var(--vscode-focusBorder)", "borderRadius": "12px", "maxWidth": "80%" } }
{ "region": "chat.landing", "replaceWith": "myLanding" }
```

| Part | What it takes |
|---|---|
| `chat.surface` | style: `backgroundColor`, one of the theme's own (below), `backgroundImage` |
| `chat.landing` | hide, replace, text style |
| `chat.landing.hero` | hide, replace |
| `chat.landing.hints` | hide |
| `chat.messages` | replace |
| `chat.rail` | hide |
| `chat.message.user`, `chat.message.assistant` | text style, `width`, `minWidth`, `maxWidth` |
| `chat.turnStats` | hide, text style, `opacity` |
| `chat.input.frame` | frame style, `backgroundColor` one of the theme's own |
| `chat.input.mode` | hide |
| `chat.input.mention`, `.browser`, `.attach`, `.imageMode`, `.quickPhrases`, `.promptOptimize`, `.mcp` | hide, order |
| `box.page` *(new)* | The page behind every Box page: `backgroundColor` one of the theme's own, `backgroundImage` |
| `quickEdit.widget` *(new)* | The Ctrl+K box: frame style, `backgroundColor` one of the theme's own |
| `tooltip` *(new)* | Breezell's tooltips: frame style, `color`, `fontSize`, `fontFamily`, `padding` |

Text style is `backgroundColor`, `backgroundImage`, `color`, `borderColor`, `borderRadius`, `borderWidth`,
`padding`, `margin`, `gap`, `boxShadow`, `fontSize` (9 to 32px), `fontWeight`, `fontFamily`, `lineHeight` (1 to 3),
`textAlign`, `letterSpacing`, `textTransform` and `transition`. Frame style is `backgroundColor`, `borderColor`,
`borderRadius`, `borderWidth`, `boxShadow` and `transition`.

A value is one plain value of that kind: no `url()`, selectors, `calc()` or a second declaration. `var()` takes
`--vscode-*` and `--breezell-*`.

- `borderWidth` goes up to 4px; `padding`, `margin`, `gap` and `borderRadius` up to 64px or 4em; only
  `borderRadius` takes a percentage (up to 50).
- `width` and `height` go up to 2000px or 100% and down to 48px or 20%, so a part cannot be made to vanish
  that way; a minimum may be 0.
- `boxShadow`: up to three layers, offsets up to 16px, blur up to 48px, spread up to 8px, so a shadow cannot
  cover what is beside its part.
- `backgroundImage`: a gradient, or an image file of your plugin's as `plugin:assets/paper.png` (png, jpg, gif,
  webp or avif, up to 2 MB).
- `transition` animates only what a plugin can set (colours, shadow, opacity), for up to a second.
- There is still no way to position, layer, transform, clip or hide anything with style.

What is on `chat.surface`, `chat.input.frame`, `box.page` and `quickEdit.widget` has to stay readable, so their
`backgroundColor` is `transparent` or `var(--vscode-<x>-background)`, with `<x>` one of `editor`, `sideBar`, `panel`,
`input`, `editorWidget`, `dropdown`, `menu`, `quickInput`, `notifications`.

When plugins disagree, the plugin whose id sorts first has it, so the outcome does not depend on which
started first. A part replaced by one plugin stays replaced if another hides it.

A page in place of `chat.messages` or `chat.landing` always offers the user a way back to the original.
And Breezell's message list comes back by itself while a tool waits for approval, a question waits for
an answer or an error is showing, and in the modes behind an unlock. The page stays loaded behind it.
Pages in `chat.messages.top` and `chat.input.above` make room in the same cases, and each of those places
takes at most a quarter of the chat's panel, however many plugins put a page there.

**No plugin can change** the account, plans, billing, upgrades, quota, custom API settings, the model
picker, Send and Stop, the context meter, tool approvals, errors, the Box's cards about these, the plugin
pages, permission dialogs or updates. These are not parts of the list, and naming one gets a clear refusal.
Tokens reach them only as the theme reaches them, and what the user must read keeps its contrast (below).

### Breezell's variables (tokens) *(new)*

```json
"tokens": {
  "bg-1": "#fffbe8", "bg-2": "#f6f1e3", "fg-1": "#2b2b2b", "border-2": "#e2d9c3",
  "accent": "#7a4b1f", "accent-fg": "#ffffff",
  "chat-font-family": "Lora, Georgia, serif", "bubble-radius": "18px", "card-shadow": "0 2px 8px rgba(0,0,0,.08)"
}
```

A token is one of Breezell's own design variables, written with or without `--breezell-`. Breezell's screens
read them where they would read the theme, so a plugin can repaint every screen at once; a token nobody sets
changes nothing.

| Tokens | What they colour or shape |
|---|---|
| `bg-1`, `bg-1-alt`, `bg-2`, `bg-2-alt`, `bg-2-hover`, `bg-3` | Backgrounds of every screen |
| `fg-0` to `fg-4` | Text, from strongest to faintest |
| `border-1` to `border-4`, `field-bg`, `field-border`, `field-border-focus`, `ring-color`, `link-color`, `warning` | Lines, fields, focus, links |
| `accent` + `accent-fg` | Buttons and the current choice (a pair, below) |
| `card`, `card-border`, `card-shadow` | Box cards and the chat's floating panels |
| `chat-font-family`, `chat-font-size`, `chat-background` | The chat panel; `chat-background` is a gradient or `plugin:` image |
| `bubble-radius`, `bubble-padding` | The user's message bubbles |
| `input-radius`, `input-shadow` | The chat box |
| `send-bg` + `send-fg`, `approve-bg` + `approve-fg`, `reject-bg` + `reject-fg`, `error-bg` + `error-fg` | Send, Apply and Reject on tool calls, error cards (pairs) |

Each takes a value of its kind, checked as a style is. **The pairs** colour what the user must always be able to
read: they are set together, both as written-out colours (`#rrggbb`, `rgb()`, `hsl()`), opaque, and with a contrast
of at least 4.5 (WCAG AA); otherwise neither is used. An error card keeps the theme's text colours whatever your
palette is, unless you set the error pair. A token may also take its value from one of your own settings, such as
a colour the user picks in Feature Options: `"link-color": { "setting": "myPlugin.accent" }` (not for a pair).
When plugins set the same token, the plugin whose id sorts first has it.

### Fonts and images *(new)*

```json
"fonts": [{ "family": "Lora", "file": "fonts/Lora.woff2" }, { "family": "Lora", "file": "fonts/Lora-Bold.woff2", "weight": "700" }]
```

A font is a `.woff2`, `.woff`, `.ttf` or `.otf` file in your plugin, up to 2 MB, at most 8. Breezell reads the file
and loads it under a name of its own, so a `fontFamily` or token of yours that names `Lora` gets your font, and no
plugin can replace a font the rest of the screen uses. An image is named as `plugin:<path>` in `backgroundImage`
or `chat-background`, read from your plugin the same way. Nothing is fetched from an address.

### A stylesheet *(new)*

```json
"stylesheet": "look.css"
```

```css
:root { --breezell-bg-1: #fffbe8; --breezell-fg-1: #2b2b2b; --breezell-chat-font-family: Lora, serif; }
::part(chat.message.user), ::part(chat.message.assistant) { border-radius: 16px; padding: 10px 14px; }
::part(box.page) { background-image: linear-gradient(#fffbe8, #f6f1e3); }
```

The file (up to 64 KB) is another way of writing tokens and patches, not CSS the screen runs: Breezell reads
`:root` rules of its variables and `::part(<name>)` rules of the parts above, with comments, and checks every value
as in `package.json`. Any other selector, an at-rule (`@import`, `@font-face`, `@media`) or `!important` is left out,
and `validate` lists each. What `package.json` declares wins over the stylesheet.

### Looks that follow your settings *(new)*

A patch or a set of tokens can hold only while one of your own settings has a value:

```json
"patches": [{ "region": "chat.landing", "style": { "padding": "8px" }, "when": { "setting": "myPlugin.dense", "value": true } }],
"tokens": [
  { "values": { "bg-1": "#fffbe8" } },
  { "values": { "bg-1": "#101418", "fg-1": "#e6e6e6" }, "when": { "setting": "myPlugin.theme", "value": "night" } }
],
"variants": {
  "setting": "myPlugin.theme",
  "values": {
    "paper": { "tokens": { "accent": "#7a4b1f", "accent-fg": "#ffffff" } },
    "night": { "tokens": { "accent": "#c8a97e", "accent-fg": "#101418" }, "patches": [{ "region": "chat.surface", "style": { "backgroundColor": "var(--vscode-editor-background)" } }] }
  }
}
```

`variants` is the same as a `when` on each of its tokens and patches. The setting must be in your own
`contributes.configuration`, and the value of its type. Put the setting in Feature Options (`ui.options`) and
the user switches your looks there; your code can switch them too, by writing its setting, and Breezell redraws.
Within your plugin a later set of tokens wins over an earlier one, so a variant wins over the base. At most 16
sets of tokens and 32 patches in all.


### Code fences

```json
{ "language": "chart", "surface": "chart" }
```

A fence in that language is drawn by that page once it is complete: until then it shows as code, and it
is given the fence's text as its context. A language for code or data, which the user has to be able to
read, copy and apply, cannot be taken (`typescript` and `ts`, `python`, `json`, `bash`, and so on), nor what
Breezell draws itself (`mermaid`, `causal`, `diff`, `markdown`, `math`): `validate` tells you. When plugins
want the same language, the plugin whose id sorts first has it.

### Modes

```json
{ "id": "reviewer", "title": "Reviewer", "description": "Reads before it writes.", "base": "agent",
  "icon": "checklist", "instructions": "modes/reviewer.md", "l10n": { "zh-TW": "審查員" },
  "descriptionL10n": { "zh-TW": "先讀再寫。" } }
```

`base` is `normal`, `plan`, `analyze` or `agent`. The mode is that mode: its tools, approvals, limits and
billing are all that mode's, and the file's text (up to 8,000 characters) is added to what the AI is told
while the mode is picked. The modes behind an unlock cannot be a base. The mode ends when the picker moves
to another mode, and it does not come back by itself. At most 4 per plugin.

### A message before it is sent

```js
vscode.breezell.chat.registerSendHandler(({ conversationId, text }) => {
	if (/sk-[A-Za-z0-9_-]{20,}/.test(text)) {
		return { cancel: true, reason: 'This message seems to hold a secret key.' };
	}
	return { text: text.replace(/\bTODO\b/g, 'to do') };   // or nothing: as it is
});
```

Needs `chat.intercept`, one handler per plugin. It covers what the user sends (typed, queued, edited or a
follow-up they picked), not what Breezell or another plugin writes: a teammate's start, a plan's prompt,
`chat.send`. The message goes on through the usual send path, so its model, plan and billing are what they
would have been.

- It sees the text as it reads, with mentions written out (`@file.ts`), and `attachments`: the names of what goes with it. Attachments stay as they are.
- Context for the AI: answer `{ context: '...' }` (alone or with `text`), up to 20,000 characters, 50,000 from all
  plugins together. The AI reads it with the message and is told it came from your plugin; the user does not see
  it in the chat and `chat.read` does not show it. It stays in the conversation's history, and an edit of the
  message asks your handler again and replaces it.
- Stopped: the user is told by which plugin and why, and the text stays in the chat box.
- A command of the plugin's own: answer `{ cancel: true, handled: true }`. The box clears and nothing is said,
  so telling the user what happened is up to the plugin. Keep `reason` for an older Breezell, which takes it as stopped.
- Changed: what is sent is what shows in the bubble, and it must not be empty or over 400,000 characters.
- An answer later than 3 seconds, or a failure, passes the message on as it was, and all plugins together get
  at most 6 seconds.
- With several plugins they go in id order, each seeing what the one before made of it.

## Windows

A window plugin declares its windows in `package.json`:

```json
"contributes": {
	"breezell": {
		"windows": [{
			"id": "timer",
			"title": "Focus Timer",
			"entry": "window/index.html",
			"width": 380, "height": 560, "minWidth": 320, "minHeight": 460,
			"requiresEditor": false
		}]
	}
}
```

- The page is the plugin's own HTML, CSS and JavaScript, loaded from `breezell-plugin://<publisher.name>/`.
  It loads `/__breezell/api.js` for `window.breezell`: `postMessage(message)` (to the plugin's code),
  `onMessage(listener)` and `connected`.
- In the plugin's code, `vscode.breezell.windows.open('timer')` opens it (or brings it to the front) and
  returns an object to `postMessage` to the page, listen to `onDidReceiveMessage`, `onDidClose`, and `close()`.
- The window is sandboxed: no Node, no network (`connect-src 'self'`), only the plugin's files, no popups,
  no navigating away, and its own storage (`localStorage`, IndexedDB) separate from Breezell and other
  plugins. The title always ends with the plugin's name.
- Window plugins need `"extensionKind": ["ui", "workspace"]`: the window's files are read on the user's computer.

**Opening without the editor**: with `"requiresEditor": false` a window can open on its own, with no editor
window: from a shortcut that **Plugins › Installed** adds (**Add to Start menu** on Windows, **Add to applications
menu** on Linux: a `.desktop` file, **Add to Applications** on macOS: a small app in `~/Applications` that
Launchpad and Spotlight find), with
`breezell://plugin-window/<publisher.name>/<window id>`, or `Breezell --plugin-window <publisher.name>/<window id>`.
It still needs a signed-in Breezell account; otherwise Breezell opens as usual. A window opened on its own
has no editor to relay messages: `window.breezell.connected` is `false` and `postMessage` resolves to `false`.

### What plugins cannot reach

To protect users and Breezell, plugins get none of these:

- The Breezell sign-in token: `vscode.authentication` gives no `breezell` session.
- API keys, the API Vault, conversation content, system prompts, cloud prompts, memories.
- Breezell's internal commands: `breezell.*` and the other Breezell commands are for Breezell and its built-in extensions only. `executeCommand` refuses them, and a `command:` link to one, in a notification, a page or a hover, does nothing.
- The commands `breezellIme.*`: Breezell hands the chat box's keys to them, so only the Breezell IME plugin (`breezell.ime`) may register them.
- Breezell's own files: the databases, chat transcripts, memories and the copies of its prompts, for `vscode.workspace.fs`, `openTextDocument`, `workspace.applyEdit` and `fs`, whichever the URI scheme or link. The app's own folders cannot be written to either, and no folder holding any of these can be copied, moved or removed in one go. A plugin's own storage and the user's files are not affected. Do not look for a way around this: review refuses a plugin that does.
- Breezell's main window: plugin code, HTML and CSS only run in their own pages (see [Changing Breezell's screens](#changing-breezells-screens)).

## Open or closed source: your choice

| | Open `--open` | Closed `--closed` |
|---|---|---|
| Package contents | Build + `src/` + source maps | Minified build and `media/` only |
| `package.json` | Needs `repository` (https) | Not required |
| In the market | "Open source" badge with a link to the source | "Closed source" badge |

Either way the market shows the package, its SHA-256 and the permissions it declares. Note that
minified JavaScript can still be read: closed source means "no source shipped", not encrypted.

## Publishing to the market

1. Fork [BreezellCode/BreezellCode](https://github.com/BreezellCode/BreezellCode) and clone your fork.
2. In the plugin folder, run `npm run package:open` (or `package:closed`).
3. Run `npm run submit -- --market ../BreezellCode`. The devkit
   - copies the `.vsix` to `plugins/packages/<id>/<version>/`;
   - updates `plugins/packages/<id>/plugin.json` (version, SHA-256, size, permissions) and copies the README and icon;
   - regenerates `plugins/index.json`.
4. Commit and push in your clone, then open a pull request to `BreezellCode/BreezellCode`.

The pull request runs the market check: every package's SHA-256 and size, id, version, permissions
and open or closed source flag must match its entry, and `index.json` must be up to date. Once a
maintainer reviews and merges it, the plugin shows up in Breezell.

**New versions**: raise `version` in `package.json`, pack and submit again. A published version's
contents never change.

### What review looks at

- Ask only for the permissions the plugin needs, and say in the README what they are for.
- Never collect accounts, passwords or API keys, and never imitate Breezell's sign-in or payment screens.
- Never work around billing or plan limits, and never download and run code that was not reviewed.
- Closed source plugins get a stricter review; maintainers may ask questions.

## Blocklist

`blocklist.json` lists plugins that must not run. Breezell downloads it (GitHub and both jsDelivr
mirrors) when it starts, every 30 minutes while it is open, and whenever the market page reloads the
index (Refresh). A window opened on its own (lite mode) downloads it too. A plugin it names:

- is turned off where it is installed, and cannot be turned back on; the user is told why once,
  with **Uninstall** (and **Restart extension host** when the plugin was already running);
- gets nothing more from `vscode.breezell` (every call fails with `BreezellBlocked`) and loses the
  windows it opened, right away, even before the extension host restarts;
- is left out of the market and cannot be installed, from the market or from a local `.vsix`;
- does not open as a window on its own (lite mode) once Breezell has the list that names it.

It works for every extension, not only Breezell plugins, so a blocked plugin cannot escape it by
dropping its `breezell` object. Plugins that were never uploaded are matched by id the same way.

The maintainers edit the file on GitHub:

```json
{
	"plugins": [
		{ "id": "publisher.name", "reason": "Sends the open files to a third-party server." },
		{ "id": "publisher.other", "versions": ["1.0.3"], "reason": "1.0.3 deletes files outside the workspace; 1.0.4 fixes it." },
		{ "publisher": "someone", "reason": "Every plugin of this publisher shows ads.", "l10n": { "zh-TW": "這個發布者的每個插件都會顯示廣告。" } }
	]
}
```

| Field | |
|---|---|
| `id` or `publisher` | One extension (`publisher.name`), or every extension of a publisher. Case does not matter. |
| `versions` | Only these versions; every version when left out. A fixed newer version is offered again as an update. |
| `reason` | Why, in English (at most 500 characters). Users see it. |
| `l10n` | The reason in other languages: `zh-CN`, `zh-TW`, `ja`, `ko`, `ru`, `es`, `pt-BR`. English is shown where there is none. |

The market check (CI) tells which entries are wrong; Breezell leaves a wrong entry out and keeps the
others. After a change, CI also clears the jsDelivr copies; Breezell counts a new entry as soon as one
source has it, and drops a removed one once every source has.
